# NetworkSharing 需求文档

版本：0.2（方向已确认，平台能力待验证）  
状态：分阶段需求；当前已实现行为以 application-sharing.md 为准
目标平台：Android、Windows 
客户端：Flutter；系统能力与跨平台逻辑：Rust（经 flutter_rust_bridge 调用）；Windows UI 参考 WinUI 3 / Fluent Design（Flutter `fluent_ui`）  
架构：MVVM

## 1. 产品目标

NetworkSharing 用于让已配对的 Android 手机与 Windows 电脑，在需要时互相提供网络接入。用户先通过配对码建立可信设备关系；之后由设备网络状态触发提示，用户确认后由提供网络的一端开启热点、向另一端传递接入信息，并引导或尝试连接。

产品分为两个方向：

1. Windows 当前离线时，Windows 请求使用 Android 手机热点。
2. Android 当前网络不可用且 Windows 已联网时，Android 请求使用 Windows 电脑热点。无需严格判断电脑当前网络来源。

配对码用于应用层确认双方正在配对同一设备；蓝牙链路用于配对期间及后续控制消息和热点配置传输。配对码本身不代表蓝牙链路已加密，配对流程必须依赖系统蓝牙配对/加密连接，或在应用层增加认证与加密。

## 2. 角色与术语

- **电脑端**：运行 Windows 版本的 NetworkSharing。
- **手机端**：运行 Android 版本的 NetworkSharing。
- **控制通道**：已配对设备间的蓝牙通信，用于状态、请求、确认和热点配置传输。
- **网络提供方**：当前开启热点并共享网络的设备。
- **网络接入方**：当前需要连接对端热点的设备。
- **热点配置**：SSID、安全类型及密码等连接所需信息，属于敏感数据。

## 3. 主要用户流程

### 3.1 首次配对

1. 两端用户分别打开应用并进入首页配对页面。
2. 一端显示短时有效、随机生成的配对码；另一端输入该码。
3. 应用通过蓝牙发现目标设备并建立连接，双方验证配对码。
4. 验证成功后，双方保存对端设备标识与配对状态，并进入设备状态页。
5. 用户可查看设备名称、连接状态和最近连接时间，并可主动解除配对。

配对码应有有效期、尝试次数限制和重新生成入口。配对双方必须明确看到成功或失败结果。蓝牙关闭、权限拒绝、设备不可发现、超时或验证码不匹配时，显示可操作的错误原因和重试方式。

### 3.2 Windows 使用 Android 手机网络

1. Windows 端在后台监测网络可用状态；判定不可用后，向用户发出通知。
2. 提示用户是否请求已配对手机提供热点。
3. 用户确认后，电脑通过蓝牙发送请求；手机端收到请求后，应展示请求来源及授权选项：一次性允许、拒绝或永久允许；若用户多次拒绝，应提供永久拒绝选项。用户也可在应用内随时更改对该设备的权限设置。
4. 手机端获准后，尝试开启系统热点，并取得热点配置。若系统要求用户确认或手动操作，则显示系统授权/设置引导。
5. 手机通过蓝牙安全通道把热点配置发送给电脑。
6. Windows 端发起连接并显示连接进度与结果；系统要求凭据或用户确认时，遵循系统交互。
7. 连接成功后双方更新状态。任一步失败都应能重试或停止共享。

### 3.3 Android 使用 Windows 电脑网络

1. Windows 端检测自身网络可用。无需识别该网络的来源。
2. Android 端在后台监测自身网络状态；不可用时，通过本地通知询问用户是否请求电脑提供热点。
3. 用户确认后，手机通过蓝牙向电脑发送请求；电脑端收到请求后，展示请求来源及授权选项：一次性允许、拒绝或永久允许；若用户多次拒绝，应提供永久拒绝选项。用户也可在应用内随时更改对该设备的权限设置。
4. 电脑端获准后，尝试开启 Windows 移动热点，并取得热点配置。若 Windows 需要用户操作或系统能力不可用，则引导用户手动开启。
5. Windows 通过蓝牙安全通道发送热点配置。
6. Android 发起 Wi-Fi 连接并报告进度和结果；若 Android 版本或设备策略要求用户在系统界面确认，则切换到系统授权/连接流程。
7. 成功后双方更新状态。热点保持开启；若在配置的空闲时长内没有已连接客户端，则自动关闭并通知双方。用户也可随时手动关闭。

## 4. 功能需求

### 4.1 配对与设备管理

- 首页提供生成配对码、输入配对码、开始/取消配对等操作。
- 配对码由安全随机源生成，具备有效期并限制连续失败尝试。
- 只有已配对设备可发起热点共享请求；
- 提供连接状态、设备名称、解除配对和重新配对能力。
- 应用偏好应跨应用重启保存在本机，包括后台监测/通知偏好、启动监测偏好、热点空闲关闭时长和请求确认模式；敏感配对密钥与热点密码不得写入普通偏好存储。
- 蓝牙断连后自动有限次数重连，并允许用户手动重连。

### 4.2 网络状态和请求

- 当前按用户 2026-11-10 确认使用可用/不可用二值判断；检测中只显示进度，不增加未知分类。并发检测百度和 Google 的 HTTPS，任一可达即在线，不要求识别上游网络来源。
- 离线自动提醒使用延迟和冷却，避免网络切换期间重复触发。
- 通知需说明请求方向、对端设备和可能的数据/流量影响。
- 请求采用请求 ID、超时和去重机制，避免重复点击造成多次开关热点。
- 两端都可拒绝请求、取消进行中的操作和结束当前共享会话。

### 4.3 热点及连接信息

- 热点首次开启由请求方发起、提供方授权驱动；会话期间保持开启。检测到配置的空闲时长内没有连接设备后自动关闭。
- SSID、密码等信息只通过已认证的加密蓝牙会话传输，不写入普通日志。
- 接入方连接成功后验证网络可用性，并将结果反馈给提供方。
- 热点配置应尽量采用系统提供的安全方式；密码以最小必要时长保存在内存中，会话结束后清除。
- 如系统限制使应用无法读取或设置热点参数、启动热点或静默连接 Wi-Fi，必须提供明确的系统设置/确认引导，不得伪报自动连接成功。
- 空闲关闭应基于热点客户端连接状态；若系统无法可靠提供客户端状态，应采用可配置的保守超时策略，并明确告知用户，不能误将短暂蓝牙断连视为 Wi-Fi 客户端空闲。

### 阶段一：需求与平台可行性验证（当前阶段）

- 确认双向使用热点的产品流程、自动化边界和用户确认节点。
- 调研并验证 Android 与 Windows 的蓝牙通信、热点开启、热点配置读取和 Wi-Fi 连接能力及系统版本差异。
- 输出协议草案、权限清单、风险与降级流程。
- 验证 Android 普通权限、修改系统设置权限、前台服务、Root 与 Shizuku 路径的能力边界和维护成本；验证 Windows 移动热点、客户端枚举和 Wi-Fi 连接能力。
- **验收**：形成按系统版本/厂商的能力矩阵；明确自动化、系统确认与手动引导路径；配对码与蓝牙安全会话绑定方案通过评审。

### 阶段二：应用骨架与配对 MVP

- 建立 Flutter MVVM 结构和 Rust bridge 边界。
- 完成配对首页、配对码校验、蓝牙发现/连接、配对信息持久化、断连与错误状态。
- **验收**：Android 与 Windows 可互相配对、重连、解除配对；无权限和超时情况有明确反馈。

### 阶段三：单向网络共享（Windows 使用手机热点）

- 实现 Windows 离线检测、请求通知、手机端确认、手机热点操作、配置安全传输、Windows Wi-Fi 连接与结果回报。
- **验收**：在支持的系统/设备组合中完成端到端连接；受限组合按降级流程完成，并准确呈现状态。

### 阶段四：反向网络共享（手机使用电脑热点）

- 实现电脑在线状态判断、手机端请求通知、电脑端确认、Windows 移动热点操作、配置传输及 Android 连接。
- **验收**：在支持的系统/设备组合中完成端到端连接；系统限制时用户可完成引导式连接。

### 阶段五：稳定性、安全与发布准备

- 覆盖后台/前台切换、蓝牙断连、网络切换、热点已开启、请求超时、应用重启等场景。
- 完成敏感信息清理、权限说明、日志脱敏、兼容性测试和发布包验证。
- **验收**：两方向流程均无错误成功提示；会话可取消/结束；失败可恢复，敏感凭据不会进入日志。

### 阶段六：扩展能力与兼容性

- 为后续传输、设备和网络能力扩展提供稳定接口、协议版本策略和模块开发说明。
- **验收**：新增一种能力实现可通过新增适配器/用例接入，不要求修改既有配对、会话状态机或其他平台实现。

## 6. MVVM 与模块边界

### Flutter 表现层

- **View**：配对页、设备状态页、请求确认界面、连接进度和设置页；只负责展示状态、收集用户操作。
- **ViewModel**：管理页面状态和用户意图，例如生成/提交配对码、接受/拒绝请求、开始/取消共享；通过 Repository 调用业务能力，不直接操作蓝牙或平台 API。
- **State**：使用明确状态模型表达未配对、配对中、已配对、请求中、等待确认、启用热点中、连接中、成功、失败和取消。

### 领域与数据层

- **Use Cases / Domain**：配对设备、请求网络、同意共享、结束会话、检查连接状态等业务规则。
- **Repositories**：统一暴露配对、蓝牙消息、网络状态、热点和连接能力；负责协调 Flutter 与 Rust/平台实现。
- **Platform adapters**：封装 Android 与 Windows 各自的权限、通知、蓝牙、热点和 Wi-Fi 系统 API。平台差异仅通过领域定义的接口向上暴露，不向 ViewModel 泄漏原生 API 类型。
- **Rust 核心**：适合承载跨平台协议编解码、请求状态机、超时/重试策略、配置验证和安全相关纯逻辑。平台专属系统 API 不应强行放进通用 Rust 核心；可由各平台插件/原生桥接实现，再由 Repository 统一调用。

Rust bridge 是 Flutter 与 Rust 的技术边界，不替代 MVVM：ViewModel 面向领域接口，领域/Repository 决定何时调用 Rust 与平台适配器。

### 6.1 自适应跨设备 UI

- Android 手机、Android 平板和 Windows 共用同一套 Flutter 页面、组件、ViewModel 与交互流程；按可用窗口宽度和输入环境采用窄屏/大屏自适应布局。Windows 通过 `fluent_ui` 使用 Fluent Design 风格组件。
- 窄屏布局面向手机单窗口与触控操作；大屏布局面向平板和 Windows 窗口，可使用更宽的导航、分栏和键盘操作。断点应依据实际可用宽度定义，而不是仅根据设备类型或操作系统名称判断。
- 平台差异只在确有系统能力差异处判断，例如 Android/Windows 后台服务、热点、Wi-Fi、蓝牙和通知实现。平台条件应封装在 Provider/Repository 或平台适配器中，不散布在页面和 ViewModel 中。
- 首期重点支持手机窄屏与 Windows/平板大屏；同一设备多窗口、跨设备连续操作及多设备同时配对留到后续阶段。领域模型和设备仓库应保留多配对设备的扩展空间，但首期交互可限制为一个活动配对设备。
- `fluent_ui` 是 Flutter 的 Fluent 风格组件库，不会把 Flutter 窗口变成原生 WinUI 3 / XAML 应用。需验证组件在 Android 上的触控、系统返回、无障碍与窄屏表现；若要求原生 WinUI 3 控件，则需另行评估 Flutter 与原生宿主互操作。
- 阶段二以同一组页面原型验证窄屏、大屏、窗口缩放、高 DPI、触控、键鼠和主题表现；避免按平台复制两套页面。

## 7. 实现难点与推荐方案

### 7.1 后台可靠运行

Android 后台执行、通知和持续监测受系统版本、电池优化和厂商后台管理影响；Windows 桌面应用也需处理登录启动、休眠唤醒和通知权限。采用平台原生后台机制：Android 按条件使用带常驻通知的前台服务并引导用户配置电池优化例外；Windows 使用生命周期明确的后台/托盘组件。权限缺失或服务被停止时提供修复入口。不能保证应用被强制停止后仍运行。

### 7.2 热点开启和连接

Android 的“允许修改系统设置”是通用设置写入授权，并不普遍授予开启个人热点、读取热点密码或静默连接 Wi-Fi 的权限。热点 API 和静默连接能力受 Android 版本、厂商、系统签名/特权权限约束。Root/Shizuku 可作为可选 Provider，但 Shizuku 本身不是 root，能力取决于系统服务接口及用户授权；不能作为所有设备都可用的默认路径。

采用能力探测与优先级回退：公开 API/系统授权路径 -> 可用的 Shizuku Provider -> 明确标记为高级选项的 Root Provider -> 系统热点面板/设置引导。各 Provider 返回结构化能力、权限缺失原因和所需用户动作。不得绕过用户授权或静默提权。Windows 侧先探测移动热点 API、驱动与策略，再退回系统热点界面。

### 7.3 自动 Wi-Fi 接入与网络切换

连接热点可能导致原网络切换、短时断网或默认路由变化。成功条件应包括 Wi-Fi 关联成功及网络探测通过，而非只依据 API 返回成功。热点配置下发后使用一次性会话标识、确认消息和超时清理；中断时先检查热点状态，避免重复开关或遗留热点。

### 7.4 热点空闲判断

系统能否枚举热点客户端并不一致。定义独立的客户端状态 Provider；有可靠客户端列表时按连接数和空闲时长关闭，无此能力时使用可配置超时并提示精度限制。关闭前再次检查，避免漫游或系统上报延迟导致误关。

### 7.5 蓝牙配对与安全

配对码验证需要和具体蓝牙连接绑定，防止附近多个会话串线。推荐在加密蓝牙通道上交换随机数并验证短码，成功后建立设备会话密钥；热点凭据加密传输并设置有效期。BLE/GATT 与经典蓝牙的后台发现和传输能力需阶段一实测后确定。

## 8. 扩展约定

- 蓝牙、网络探测、热点控制、Wi-Fi 加入、通知和客户端枚举分别定义能力接口；每个平台和提权方式实现独立适配器，报告 `supported`、`requires_user_action`、`unavailable` 或 `permission_denied`。
- 共享流程使用方向无关的 `NetworkShareSession`，包含会话 ID、请求方、提供方、状态、超时、失败码和能力来源。UI 不依赖具体热点实现。
- 控制消息包含协议版本、消息类型、会话 ID、请求 ID、发送序号及可选字段。未知消息可安全拒绝；版本不兼容时提示升级。不得复用旧消息类型表达不同语义。
- 新功能先补充 `documents/` 专题需求与验收标准，再定义领域接口/状态/错误码，最后接入适配器、ViewModel 和 UI。跨平台能力需提供两个平台实现或明确声明平台支持范围。
- 文档维护决策、协议兼容影响、最低系统版本变化和迁移要求；重要协议变更须有版本与迁移说明。
- 建议文档：`documents/requirements.md`（产品需求）、`documents/architecture.md`（模块与依赖规则）、`documents/protocol.md`（蓝牙消息协议）、`documents/platform-capabilities.md`（权限/能力矩阵）、`documents/decisions/`（架构决策记录）。

## 9. 安全、权限与平台约束

- 配对码应短时有效、不可预测并限制尝试；生产环境还需防止重放和冒充。
- 热点密码、设备标识和配对凭据按敏感数据处理；传输加密、日志脱敏、最小化保存。
- 蓝牙发现/连接、附近设备、通知、后台网络监测、热点和 Wi-Fi 连接均可能需要系统权限或用户操作，具体授权模型按 Android 版本及 Windows API/设备策略验证。
- Android 普通应用通常受系统版本、厂商实现及权限策略限制，可能无法任意静默开启热点、读取热点密码或静默加入 Wi-Fi。Windows 移动热点也受系统 API、网卡驱动和网络共享策略影响。
因此“自动开启热点并自动连接”是目标体验，不作为未经平台验证的绝对保证；高级 Provider 作为用户显式启用的可选能力，普通权限和系统引导路径仍须可用。

## 10. 当前范围与暂不承诺

- 当前仅覆盖 Android 与 Windows 客户端；iOS、macOS、Linux 不在本期范围。
- 目标是在应用处于后台时持续监测并通知；不承诺系统强制停止应用、设备重启尚未启动服务、权限被撤销或设备策略禁止时仍自动运行。
- 暂不定义云端账号、远程配对、互联网中继或多设备同时共享。
- 阶段一验证后再确定最低 Android 版本、Windows 版本、蓝牙协议（BLE/GATT 或其他方案）以及热点能力的具体实现路径。

## 11. 已确认的产品决策

1. 配对使用一端显示、另一端输入配对码。
2. 热点保持开启；一段可配置时长内没有连接设备后自动关闭，默认空闲时长待交互设计确定。
3. 期望完全后台监测和通知；必要时引导开放后台运行/电池优化权限。
4. 普通应用无法自动开热点时，探测可用 Shizuku 或 Root Provider；不具备条件则引导通过系统界面操作。
5. 电脑只需确认网络可用，不强制识别上游网络来源。
6. Android 手机、平板和 Windows 共用 Flutter 页面与交互流程，以窄屏/大屏自适应布局适配；Windows 使用 `fluent_ui` 风格组件。平台判断集中在系统能力适配层。多设备管理留待后续阶段。
