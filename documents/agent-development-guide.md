# 后续 Agent 开发约定与可复用工作流

更新：2026-11-10。本文将用户在开发过程中多次确认的要求汇总为可复用指导，可作为以后拆分 Codex Skills 的素材；当前只是项目文档，未安装任何全局 Skill。新用户指令优先于本文，平台真实执行限制也必须遵守。

## 1. 先检索，再实现

实现功能或排查平台问题前，优先检索 GitHub 等活跃开源社区、官方文档和系统示例，寻找类似项目；不要在已有可靠方案时重复造轮子。借鉴前核对系统版本、维护状态、许可证及依赖代价，记录来源链接、实际采用的 API、复制与否和本项目适配差异。

网络不可用时，可使用用户提供的 127.0.0.1:10808 代理或本机 set-proxy.ps1；GitHub 访问可使用 set-github-token.ps1 所设置的令牌。只在当前进程使用凭据，禁止把 token 输出到控制台、文档、提交或日志。请求成功必须检查返回内容，空输出不能当作成功。

命令示例只表达调用方式，不要把 token 内容填进示例：

~~~powershell
. C:\Users\caten\.local\bin\set-proxy.ps1
fvm flutter pub get
~~~

## 2. 功能优先，积极验证平台方案

用户要求先积极完成可用功能，后期统一处理安全加固和相关边界说明。当前已授权的开发/Debug 阶段可以通过应用配对后的蓝牙发送热点凭据，用于联调；不要仅因未来加密、密钥库或发布安全工作尚未完成而停下功能开发，也不要把系统设置入口等同于已经实现自动控制。

Android 热点普通权限不足时，继续研究并尝试 Root、Shizuku 或合适系统 API；必要且兼容依赖时可以提高 SDK。是否具备能力以当前机型实际返回和日志为准。不得伪报功能成功，也不要把某台设备上的成功推断为所有系统版本支持。

用户倾向命令优先获得可用权限，尤其曾遇到“无输出但未执行”的情况；Agent 必须服从当前工具权限策略。当前若禁止提权参数，就使用允许的执行方式、核实退出码与结果，必要时改用原生 PowerShell 5.1，不能伪称已提权或因历史要求反复请求确认。

## 3. 工程工具与分支

- Flutter/Dart 统一使用 fvm flutter / fvm dart。当前采用 Flutter stable 和最新版兼容 fluent_ui，具体锁定版本看 .fvmrc、pubspec.yaml、pubspec.lock。
- 真实工作路径以当前磁盘和 Git 根目录为准；用户已把项目迁移到英文目录 C:/Users/caten/Desktop/school/renzhizuoye/second/networksharing，环境残留的中文旧路径不能继续沿用。
- 保持 debug 分支逐步提交，在完成可运行阶段后合入 master。用户说“先 commit 和 merge”时先做这一步，已提交且干净的工作区不制造空提交。
- 保留用户本地改动和不相关文件，例如当前未跟踪 devtools_options.yaml；提交时明确选文件，不盲目 git add 全目录。
- 构建被运行中的 EXE 占用时说明实际原因，使用独立输出或等待用户退出；不要未经授权杀掉无关进程。双端大构建尽量串行，避免开发机内存耗尽。

## 4. 架构与页面

采用 MVVM：页面展示和收集操作，ViewModel 管理可观察状态，Repository/Provider 封装 BLE、网络、通知与平台 API。Android 手机/平板和 Windows 共享 Fluent UI 页面，按大屏/窄屏适配；平台判断集中于系统能力层。窄屏导航放底部，Windows 字体用系统中文字体。

目标是 Rust 承载通信与协议，通过 flutter_rust_bridge 自动生成桥接；蓝牙调研优先考虑用户指定 btleplug。现阶段 BLE 与热点/Wi-Fi 仍部分由 Flutter 插件、Kotlin 和 PowerShell Provider 执行，不得声称已经完成 Rust 迁移。扩展应保留稳定能力接口并记录当前实际边界。

设置使用 shared_preferences 持久化；跨后台 isolate 读写优先 SharedPreferencesAsync，避免缓存不一致。设备配对记录、实时在线状态和当前共享会话是不同状态，不能用“保存过设备”直接显示在线。

## 5. 正常应用行为

- 手机主动发现电脑；首次输入电脑配对码，之后启动时主动恢复保存的连接并周期重试。Windows 持续广播，关闭主窗口默认进托盘，无关闭选择对话框。
- Android 前台服务支持后台运行；必要时引导通知/后台权限。通知“允许开启”直接在后台触发，不主动跳回主界面。不要在后台 isolate 创建第二份竞争 BLE 会话。
- 网络探测并发使用 www.baidu.com 和 www.google.com，任一可达即可判在线。用户已明确暂不要求额外区分“未知”和“离线”；现实现为 HTTPS 探测，不能描述成真实 ICMP ping。
- 新认证连接建立稍后发送一次本机网络情况；设备在线状态由心跳/链路恢复实时更新。热点生命周期不依赖短时 BLE 断开。
- 已配对设备用独立磁贴，管理是否自动同意、自动拒绝或每次询问；授权持久化并在正常共享流程生效。多设备仅规划，本轮保持单一活动 peer。
- 新功能需同时考虑开始、等待、确认、成功、失败、取消、重试与重启，不只把 Debug 按钮做通。只有真实关联和网络验证通过才能显示完整联网成功。

## 6. 日志与可测试性

按钮点击、发现设备、认证/恢复、通知动作、热点与 Wi-Fi 调用、共享状态转换都应写入结构化文件日志，方便用户导出。Windows 和 Android 都要能找到文件；用状态、请求关联 ID、错误类型和平台错误码帮助定位，避免只写“失败”。日志不要包含热点密码、配对码正文、恢复令牌和 token。

异步流程使用 request/session ID、超时、去重和取消失效机制，防止重复点击、旧通知及迟到结果触发新操作。可注入时间源、网络 Provider 和通知回调用于真正有意义的测试；避免为简单可逆 UI 改动堆积实现镜像测试。

## 7. 验证和交付节奏

用户不要求每轮严格完整验收。先完成有意义的自动化验证和双端构建；当主要使用流程接近完整时主动通知用户实机测试。继续修复文档要求的使用缺陷，不因后期安全事项无限推迟可测试版本。

编译通过、模拟 Provider 通过和双端实测是不同证据；报告时分别说明。现用户已确认上一版 Debug 项目可用，本轮完整共享和新的后台通知链路仍需真实手机/Windows 验证。用户明确标记为主动触发的错误（例如一次 Windows 开热点失败）不要重新当缺陷追查。

交付说明给出变更、实际通过的检查、产物绝对路径、Git 提交/合并结果和最有价值的少量实机步骤。测试完成后不要无理由反复重跑全部检查。
